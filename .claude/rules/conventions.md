# 프로젝트 작업 규칙 (사용자 지정)

## 브랜치 / PR 올리는 절차
세션마다 반복되던 사고를 막기 위한 규칙이다. **작업을 시작하기 전에 이 순서를 따른다.**

1. **먼저 원격 상태를 확인한다** — `git fetch origin master` 후
   `git log --oneline origin/master -3`.
2. **지정 브랜치가 이미 머지됐는지 본다** — `git branch -r --contains <브랜치 HEAD>`에
   `origin/master`가 나오거나, 그 브랜치의 PR이 merged면 **그 브랜치는 끝난 것**이다.
   머지된 히스토리 위에 새 커밋을 쌓지 말고 master에서 새로 뻗는다:
   `git checkout -b claude/<새-이름> origin/master`. 새 작업 = 새 브랜치 = 새 PR.
   (머지 후 삭제된 브랜치는 같은 이름으로 push하면 되살아난다 — 이게 사고의 원인이었다.)
3. **푸시 직전에 확인한다** — `git log --oneline origin/master..HEAD`에 이번 작업 커밋만
   보여야 한다. 머지 커밋이나 남의 커밋이 섞였으면 브랜치를 잘못 만든 것이다.
4. **작업이 끝나면 PR까지 연다.** 매번 따로 요청하지 않아도 된다. push만 하고 멈추지 않는다.
5. **머지된 PR의 제목·본문은 절대 수정하지 않는다.** 기록이 실제 배포된 내용과 어긋나고,
   배포 전이라면 잘못된 공지가 디스코드로 나간다. 후속 내용은 새 PR에 쓴다.
6. 브랜치 삭제(`git push --delete`)는 이 환경에서 막혀 있다 — 정리가 필요하면 사람에게 알린다.

PR 본문은 이 순서로 쓴다 (`deploy/README.md`의 공지 파서 형식):

```markdown
## 요약
개발자용 상세 — 스키마·API·구조 변경 등          ← 공지에 안 나감

## 공지
🏷️ 한 줄 헤드라인 + 유저 관점 2~4줄              ← 이 부분만 채널에 게시됨

## 테스트
검증한 내용                                      ← 다음 H2부터 제외
```

## PR / 커밋
- PR 제목·본문은 **한국어**로 작성한다.
- PR 본문에 "Generated with Claude Code" 등 Claude 관련 문구를 넣지 않는다.
- 유저에게 알릴 만한 변경이면 PR 본문에 `## 공지` H2 섹션을 넣는다 — master 머지·배포
  성공 시 그 섹션만 디스코드 공지 채널에 자동 게시된다 (`deploy/README.md` 참고,
  다음 `## ` 헤딩 전까지가 공지 내용). 공지할 게 없으면 섹션을 생략한다.
- 관리자/개발자용 변경(업로드 UX, 내부 리팩토링 등)은 공지에서 제외하고
  유저 체감 변화(새 기능, 채점 정책, 버그 수정)만 공지에 담는다.

## 유저 개인 설정 저장 위치
- 유저 개인 설정은 **계정(서버)** 에 저장한다 — `user_preferences` 테이블 +
  `GET/PUT /api/users/me/preferences`. 설정을 추가할 때는 컬럼·필드를 늘린다.
- 특히 **마이페이지(내 계정)에 노출되는 설정을 localStorage에 두지 않는다** — 계정 설정처럼
  보이지만 기기마다 따로 놀고, 공용 PC에서는 로그아웃해도 남는다.
- **기기에 매인 설정만** localStorage에 둔다 (에디터 글꼴·글씨 크기·줄바꿈, 작성 중인 코드 draft).
- 판단 기준: "다른 기기에서 로그인했을 때 따라와야 하는가?" → 예면 서버, 아니면 localStorage.

## 채점 정보 노출 정책 (백준 기준)
- 시간/메모리는 **정답(ACCEPTED)일 때만** 노출한다.
- 테스트케이스 **개수는 비공개** — 채점 중에는 진행률 %만 보여준다.
- 비공개 테스트 데이터를 탐침할 수 있는 정보 노출을 피한다.

## 문제/테스트케이스
- 대용량 테스트케이스는 원시 데이터 대신 **생성기 양식**(`.md`의 `<!-- @generator -->`,
  시드 기반)으로 관리한다. 시드가 같으면 데이터가 바이트 단위로 재현된다.
- 생성기에는 가능하면 `~~~validator`(독립 구현 두 번째 정답)를 붙여 케이스를 검증한다.
- nginx 본문 제한(1MB)은 올리지 않는다 — 업로드는 앱 레벨(생성기/분할 업로드)로 해결한다.
- 지문 이미지는 S3(`deploy/aws-s3-images.md`)로 올리되, 간단한 도형·다이어그램은
  인라인 SVG를 권장한다 (가볍고 확대해도 선명).

## 작업 방식
- 방향이 갈리는 결정은 질문을 최소화하고 합리적 기본값으로 진행한 뒤 사후 보고한다.
- 인프라(Judge0 박스 등) 수동 작업이 필요한 변경은 "박스에서 할 일"과
  "PR로 자동 반영되는 것"을 구분해 문서화한다 (`deploy/judge0/README.md` 예시).
